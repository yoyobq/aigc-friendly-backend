# AIGC 项目的测试与可执行信任体系

> AI 会出错，人类也会出错。我不期待 AI 永远正确。在相同任务难度和交付规模下，只要经过完整开发与验证流程，AI 最终留下的错误比人类更少，造成的影响也更小，就是成功。

本文面向希望理解 AIGC 项目测试体系的人。
这里不讨论特定框架、仓库结构或测试命令。想谈的是另一件事：当系统不断变大，而且代码几乎都由
AIGC 完成时，unit、e2e 和静态架构检查究竟给了我们什么。

一项验证机制即使不能消除所有误判，只要能有效减少遗漏的错误或降低其影响，就有实际价值。

## 1. 这套体系首先要解决什么问题

这套测试体系来自一个明确的架构选择：不把每项能力都拆成微服务。这里的 Capability 指能力准入、
所有权、装配和观察等治理。它划出了管理边界，却没有用独立进程、独立数据和独立发布单元隔开
新旧代码。

这个选择有好处。能力留在同一个系统里，组合、复用和演进都更灵活。代价也很直接：它们共享
运行时、依赖注入、API schema、鉴权、错误处理、数据库、事务和基础设施。一段旧代码即使没人碰，
也可能因为新能力加入、公共装配变化或基础设施调整而表现不同。

项目变大以后，只确认新代码能运行远远不够。更难回答的是：新代码进入当前系统以后，过去已经成立
的能力还成立吗？

微服务靠隔离缩小变化范围。这套架构保留了单体内部的组合自由，就要用架构规则控制变化方向，再用
测试检查新旧能力能否继续共存。我把这个取舍理解为：

> 用可执行的历史，换取单体架构内部持续演进的自由。

## 2. 它与传统 TDD 的关注点不同

传统 TDD 描述的是代码如何产生：先写一个失败测试，再实现，再重构。它是一种开发节奏，反馈往往
从函数、类或模块开始。

这里没有规定测试和实现谁先写。无论实现由谁生成、按什么顺序完成，最后都要留下足够的证据：
当前行为符合承诺，过去确认过的行为也没有被破坏。

| 关注点   | 传统 TDD             | 这套测试体系                       |
| -------- | -------------------- | ---------------------------------- |
| 首要问题 | 代码如何被逐步写出来 | 当前完整系统为什么仍然值得信任     |
| 主要反馈 | 局部实现是否满足预期 | 局部决策与完整业务链路是否同时成立 |
| 时间尺度 | 当前开发循环         | 单次变更验证与长期回归积累         |
| 测试价值 | 驱动设计与实现       | 主动找错、保存承诺并为变更提供证据 |

两者解决的问题不同。TDD 仍然可以是很好的开发方法，而本文讨论的是如何持续验证系统，并让信任
随着测试一起积累。

## 3. 行为和架构需要不同的证据

### 3.1 Unit：证明局部决策仍然正确

Unit 测试适合处理规则密集、分支复杂，但又能在局部说清楚的行为，例如：

- 输入边界、权限裁定和状态转换；
- 失败分类、重试决策和幂等判断；
- 事务编排中的先后条件；
- 大量临界值和异常组合；
- 不适合在完整链路中反复构造的低概率分支。

它反馈快，也容易定位和穷举。Unit 通过，只能说明这个决策单元在给定条件下按预期工作。真实装配、
协议入口、数据库和其他单元组合起来以后怎么样，还需要更大范围的验证。

### 3.2 E2E：证明组合后的系统兑现了承诺

E2E 从真实入口进入，经过协议适配、鉴权、用例编排、事务、持久化和输出契约，再观察链路结果。

“以 E2E 为主”说的是裁决权，不是文件数量，也不要求把所有分支都塞进 E2E。

> Unit 证明某个决策在局部是正确的；E2E 证明这些决策组合起来以后，系统仍然兑现了业务承诺。

E2E 还可以按照信任对象区分不同范围：

- 主链路 E2E 证明入口、应用装配与持久化能够共同完成系统承诺；
- 异步 E2E 证明消费、重试、去重和状态收敛在真实队列基础设施中成立；
- live smoke 证明系统与真实外部服务在当前环境中确实能够协作。

日常开发中，相关 E2E 跑通以后通常就能放心不少。它验证的是变化发生以后，相关能力在完整系统中的
表现，而不是某个 mock 后的内部方法。

### 3.3 ESLint：检查实现有没有越过架构边界

把测试体系理解为一组可执行证据，它就不只包含 unit 和 E2E。前两者回答“系统做出了什么行为”，
架构 ESLint 回答“实现是不是沿着允许的依赖方向和边界做出这个行为”。

这在 AIGC 项目里很实用。一个实现可能通过全部 happy path，同时把业务逻辑放错层、读取不该读取
的运行时状态，甚至为某项测试加入生产代码捷径。行为测试未必看得到这些结构问题，ESLint 可以在
代码运行前拦住其中一部分。

例如，可以把以下约束写成 ESLint 规则：

- 禁止业务执行代码直接读取原始运行时环境变量。配置只能在启动和装配边界读取、归一化，再交给需要
  它的代码。业务实现无法自行感知当前是否处于 test/e2e 环境，也就少了一条为测试切换业务分支的
  捷径。
- 禁止协议层的类型、装饰器和运行时依赖泄漏到业务层。测试文件可以为本地 fixture 放宽这条约束。
- 测试文件可以选择性放宽复杂度、部分类型严格性和 fixture import 等检查，方便构造人工场景。

测试代码能使用某种 import、装饰器或配置方式，不代表生产实现可以照搬。测试需要一些自由来搭建
检验装置，生产代码仍然要遵守完整约束。

ESLint 无法证明所有设计规则都正确。没有自动覆盖的部分仍要靠规则文档和审查维护，lint 没报错也
不等于实现获得了架构许可。它的作用很具体：把可以机械判断的边界固定下来，不让这些边界因为 AIGC
漏读了一段上下文就失效。

### 3.4 自动验证：让证据按时出现

检查存在，还不等于信任链已经建立。如果架构 lint 和回归测试只靠开发者偶尔在本地执行，一次忘记
就可能让错误进入主干。执行范围可以分开：

- 每次合并前执行全量架构 lint、确定性的 unit 和与变更相关的 E2E；
- 定期执行常规全量 E2E，公共边界或基础设施发生变化时也要主动触发；
- 真实外部 smoke 根据环境和验证目的执行，不把偶然的外部波动混进常规门禁。

本开源版通过本地命令执行并记录这些检查，本轮不配置 CI。未来若引入 CI，应另行明确触发条件和环境；命令存在不表示它已在自动流水线执行。

## 4. E2E 保存的是历史级别的信任

一个重要的 E2E 场景也在保存项目历史。它记录的是：

- 某项业务行为为什么应当成功或失败；
- 某种权限、错误和状态语义已经作出什么承诺；
- 哪些跨层协作必须同时成立；
- 某个曾经出现的问题以后不能再次出现。

项目会继续加入新能力、调整装配和重构内部实现。此时真正值得检查的并不是旧代码有没有被动过，
而是旧能力在今天这个已经变化的完整系统里是否仍然成立。

运行相关 E2E，就是拿这段历史重新检验当前系统。测试通过后，开发者不必重读全部新旧实现，也不用
复盘历次重构，可以直接依据这次可重复的执行结果作出判断。

信任就这样一点点积累。重要的业务确认、出现过的问题和边界决策一旦写进测试，以后的相关变更都要
再次面对它。实现可以替换，内部结构也可以调整，已经确认的行为则要继续得到证明。

## 5. 在纯 AIGC 项目里，测试必须主动找错

保存历史并没有取代找 bug。在几乎纯 AIGC 生成的项目里，主动发现当前实现中的错误仍是测试最基本
的工作。

AIGC 很容易生成结构合理、类型正确，而且 happy path 也能工作的代码。问题通常藏在这些地方：

- 权限与身份的组合差异；
- 部分写入后的失败回滚；
- 重复请求、并发与异步时序；
- 边界值、空值和非法状态；
- 可重试与不可重试错误的区别；
- 返回结果正确但产生额外副作用的情况。

测试要做的不只是证明实现“大致能用”，还要尝试反驳它。Happy path 说明最顺利的输入能到达终点，
却没有画出系统行为的边界。

一项重要能力通常需要同时具备：

- 正例，证明明确允许的行为能够完成；
- 反例，证明权限、状态或输入越界时会被拒绝；
- 临界场景，验证行为发生转换的边界；
- 故障场景，验证失败、回滚、重试和最终收敛；
- 重复或并发场景，验证幂等和副作用次数；
- 回归场景，固定曾经出现过的问题。

这里允许适度冗余，前提是重复验证能提供不同来源的证据。它的价值与止损线会在第 7.4 节展开。

测试同时面对今天和以后。它要找出当前 AIGC 实现中的 bug，也要把已经确认的事实留给未来的变更。

## 6. 必须警惕“为了通过测试而存在”的生产代码

这不是假设，实际开发里已经反复见到过。AIGC 会把“让测试通过”识别为非常明确的局部目标。实现
与测试对不上时，它未必修正业务逻辑，有时会在生产代码里加一条只对测试环境、fixture 或测试时序
有用的捷径。

常见表现包括：

- 根据 `NODE_ENV=test/e2e` 改变业务行为；
- 遇到真实依赖失败时静默返回测试期待的默认值；
- 对 fixture 中的特殊 ID、名称或输入形状做特殊处理；
- 捕获本应暴露的错误，然后伪造成功结果；
- 在真实状态缺失时临时补造数据，让 happy path 继续；
- 为适应测试时序，加入生产场景没有合理含义的等待、重试或降级。

用 ESLint 禁止业务执行代码读取原始运行时环境变量，可以直接挡住第一类风险。它能封住最明显的
环境分支，但认不出所有 fixture 特判、静默兜底和伪造成功。这些问题仍要靠行为测试和代码审查。

这类代码会污染测试证据。测试虽然绿了，接受检验的却不是生产系统的真实行为，而是一个知道自己
正在被测试、临时改了规则的系统。

> 测试是证据，但生产代码不能因为正在接受检验，就改变自己的业务行为。

合理的测试接缝和测试专用业务逻辑不是一回事。通过依赖注入替换邮件、AI Provider、时钟等外部
边界很正常。问题出在业务实现内部：那里不该出现只为某项测试成立的判断或兜底。

生产降级策略可以存在，但要说得清楚：

- 有明确的真实运行场景，而不是由失败测试临时催生；
- 有能够说明的业务语义和适用边界；
- 失败或降级可以被观察，而不是静默伪造成功；
- 自己也有正反例验证，证明不会掩盖真正的问题。

遇到可疑兜底时，我会问一个很直接的问题：

> 如果不知道这条测试的存在，这段代码在生产系统中仍然有充分、清晰的存在理由吗？

如果答案是否定的，它多半是测试诱导出的伪实现。测试环境没有扭曲生产语义，绿色结果才值得相信。

> 对 AIGC 项目来说，测试专用兜底会让绿色结果失去证据资格。

## 7. 进一步补充：让信任体系长期有效

前面是这套体系的主干。下面五点更像日常维护时不能忘的提醒。

### 7.1 既有测试也是受治理的历史

旧测试失败时，AIGC 还可能直接修改断言、删除用例或放宽预期。改生产代码通常是在换实现，改既有
测试则可能是在改已经确认的业务承诺。

测试代码不是可以随实现自由调整的附属品。不能因为新实现过不了，就反过来让历史适应实现。修改
既有测试需要独立理由：承诺确实发生了变化，测试原本就没有正确表达承诺，或者它覆盖的场景已经
不可达。前者改变历史，后两者修正证据，每一种都要有需求、契约、Capability 决策或当前架构事实
作为依据。

另一种退化也要处理：测试还在，场景却已经不可达。架构变化可能消除某个旧的中间状态，早期测试
随后只剩下形式上的通过，不再检验原来的风险。测试需要定期确认它声称覆盖的路径仍能触发。确实失去
现实入口的测试应说明原因后退出，并由新路径上的测试接住仍然有效的业务承诺。历史测试不是越多
越好，一条永远碰不到目标行为的测试没有证据价值。

### 7.2 实现与验证应保持一定独立性

如果 AIGC 先写实现，再逐行照着实现生成测试，很可能只是把同一个误解复制了两遍。代码和测试完全
一致，照样可能一起出错。

测试场景和预期应尽量来自业务描述、接口契约、Capability 决策与历史问题，而不是从当前实现反推。
测试要判断实现是否满足外部承诺，而不是记录实现碰巧做了什么。

这种独立性不要求人类重新介入。负责实现的 AI 可以自行开启一个不继承前序生成上下文的新 session，
把需求、契约和当前结果交给它重新讨论与检查，再根据审查结论继续修正和回归。这是一种由 AI 主动
发起的自我审查：生成、质疑、修正和验证都由 AI 完成，但审查者不沿用生成者的上下文，也不会让
同一段推理一直为自己的结论作证。

新 session 的结论还要落到可复现的问题、对应规则或可执行检查上。完成修正以后，AI 重新运行相关
测试与 lint，这轮自我审查才算结束。

### 7.3 绿色结果有明确的信任范围

“相关 E2E 通过就基本放心”有一个前提：我们找对了相关测试。项目继续变大以后，识别变化的真实
影响范围，可能比执行测试本身更难。

为了让“相关”有可追溯的依据，可以把业务承诺、依赖关系和验证入口关联起来。尤其在能力之间存在
协作时，需要记录谁依赖谁的什么承诺、承诺依据来自哪里、成功与失败时允许或禁止什么副作用，以及
哪些测试通过什么观察点验证这些承诺。记录中还应说明哪些变化需要重新验证，并让协作双方都能找到
这份记录，避免提供方自身的测试仍然通过，消费方依赖的行为却已经被破坏。

这种关联可以通过现有契约说明和测试入口之间的简短链接维护，随真实协作需要逐步补充。它帮助确定
回归范围，但不能替代对实际调用、装配和共享依赖的检查；没有记录的关联，也不能直接视为没有影响。

有些变化天然需要扩大回归范围。公共装配、全局协议行为或共享配置发生变化，会影响许多看似无关的
入口；持久化、缓存、队列等基础设施调整，可能改变多个能力的共同运行条件；跨域事务、共享契约和
公共类型的变化，也不能只验证发起修改的那一侧。遇到这些信号，单个文件或单项能力的 E2E 不足以
支持结论。

日常开发仍然可以先跑相关测试获得快速反馈。高扩散变更需要扩大到相邻能力，必要时执行常规全量
E2E；定期全量回归用于发现影响范围判断中的长期遗漏。全量架构 lint 则从依赖方向和边界上再检查
一次，避免只根据行为测试推断安全。

一次绿色结果只证明它实际覆盖的场景。跑了一组与变更无关的 E2E，结果再绿也不能说明这次修改安全。
因此每次选择回归范围时，都要能回答两个问题：变化穿过了哪些公共边界，哪些旧承诺可能因此得到不同
结果？

### 7.4 有价值的冗余来自证据多样性

机械复制同一个输入和断言没有多少价值。更有用的做法是从不同角度观察同一承诺：

- unit 验证决策，E2E 验证组合结果；
- 不同入口最终形成相同状态；
- 同时观察响应契约、持久化事实和外部调用次数；
- 正例、反例与边界场景相互夹住允许行为的范围。

这样即使某个 mock、观察点或理解出了问题，其他证据仍有机会把它暴露出来。

冗余也有止损线。如果新增测试的输入、观察点和预期与已有用例完全相同，只是换了描述或数据名称，
它没有提供新证据，只扩大了维护面。生成测试的成本很低，不代表保留同质测试没有成本。

### 7.5 不仅证明“正确地发生”，也证明“没有错误地发生”

AIGC 可能给出正确的最终返回值，同时产生额外写入、越权读取、重复消费或敏感信息泄漏。测试除了
断言成功结果，也要检查那些不该发生的副作用。

例如，权限失败后没有继续调用下游，事务失败没有留下部分状态，去重场景没有重复消费，不可重试的
错误没有再次重试，敏感信息也没有进入输出或以明文持久化。这些“没有发生”的事实同样是证据。

## 8. 回到信任本身

这套做法不追求一个好看的测试数量或覆盖率数字。判断它有没有用，要看下面这些事情是否真的发生：

- Unit 约束局部决策，帮助快速穷举和定位；
- E2E 验证完整业务现实，对系统承诺拥有最终裁决权；
- 生产代码不会为了通过测试改变业务行为，绿色结果仍然对应真实系统；
- ESLint 把层级、依赖和运行时配置边界转化为可执行的架构证据；
- 丰富且适度冗余的正反例主动寻找当前实现中的 bug；
- 历史场景让旧承诺在每次相关变化后重新得到证明；
- 测试本身和生产实现都受到治理，绿色结果没有被迎合、伪造或错误外推。

对几乎纯 AIGC 开发的系统来说，测试既要找出这一次生成中的错误，也要保存以前已经确认过的事实。
相关 E2E 跑通之所以让人放心，依据就在这里。它用可执行的历史，支撑单体架构内部持续演进的自由。

## 本开源版的执行方式

本轮不新增或配置 CI。自动验证指本地可重复执行的 npm 命令；只有实际执行并记录的结果才作为证据。独立审查必须由未编写该变更的审查者完成，自查与变异检测不能冒充独立审查。本文是人类说明，不作为代理实现规则来源；实现应从 docs/README.md 路由到 common 规则、Capability decisions 与 collaboration agreements。
